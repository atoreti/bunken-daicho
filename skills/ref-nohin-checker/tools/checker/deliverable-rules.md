# 納品物チェッカー 規則表

自作スキルの納品物を機械照合するスクリプト `check_deliverable.py` が何を検査するかの一覧。
**スキルではない**(SKILL.md を持たないフォルダはスキルとして認識されない)。発動判定が要らないので、
各スキルの完了工程から呼ぶだけで使える。

## 原則

1. **既存の SKILL.md・references に書かれた規則の機械化に限る。** 新しい品質基準を発明しない。
2. **すべての規則に原典がある。** 原典を確認できない項目は規則表に入れない。
   ★**2026-08-18 に53規則すべてが逐語で指すようになった**(下の「原典欄の読み方」。行番号を持たないので腐らない)。
   ★**同日、機械化を見送った8項目も逐語を持った**(申-5)。さらに**判定の理由・水準表・この表の散文**に
   残っていた手書きも逐語にした(申-2〜申-4)。**この規則表に手書きの file:line は1つも無い。**
3. **判定に人間の解釈が要る項目は判定しない。** 「要目視(△)」または「未検査(―)」として理由つきで残す。
4. **違反ゼロのときも「何を検査したか」を全項目分出力する。** 検査していない項目を検査済みと誤解させない。

## 使い方

```bash
python "$HOME/.claude/skills/tools/checker/check_deliverable.py" <ファイル> [<ファイル> ...]
```

`$HOME` を使うのは、PowerShell が native exe の引数中の `~` を展開しないため(実測確認済み)。
`"$HOME/..."` はダブルクォートつきなら PowerShell・Git Bash の両方で解決する。
スキルの正典・claude.ai ミラーのどちらから実行されても同じ1本を指す。

| オプション | 用途 |
|---|---|
| `--type run-uradori\|bunken\|ronbun\|html` | 種別を明示する(既定は auto。手がかりが無いと原稿として検査するので、台帳なら明示が安全) |
| `--artifact` | この納品物を **HTML のアーティファクトとして扱う**(DOCTYPE を書かないのが正)。**種別の宣言でもある** —— `--type` を付けなければ拡張子に関わらず html として検査する。`--type html` との併用は原典どおりの正規形。**`--type ronbun`・`uradori`・`bunken` との併用はエラー(終了コード 2・検査を1本も走らせない)** |
| `--expect-count N` `--count-pattern RE` | H-5 全量保持。入力の件数と、HTML 内で数える正規表現 |
| `--max-findings N` | 1規則あたりの表示件数(既定12、0で全件) |
| `--list-rules` | 実装されている規則の一覧を出力 |

終了コード: **違反(✕)が1件でもあれば 1**、違反は無いが**検査不能(▲)が残っていれば 3**、どちらも無ければ 0。
要目視(△)・未検査(―)は終了コードに影響しない。
★**3 は「違反が無かった」ではない**——「検査そのものが走らなかった」の意味である(段5・2026-08-19)。
両方あるときに 1 を返すのは、より具体的な指示を優先するためであって ▲ を軽く見るからではない。
~~終了コード: **違反(✕)が1件でもあれば 1**、なければ 0。~~(★2026-08-19 に 3 が増えた。上が正)

出力の記号: `○` 合格 / `✕` 違反 / `△` 要目視(自動判定しない) / `―` 未検査 / `▲` 検査不能

**`―` と `▲` は意味が違う(2026-08-04 に分離)**:

| 記号 | 意味 | 終了コードへの出方 |
|---|---|---|
| `―` 未検査 | **規定によりこの納品物には適用されない**項目(検査しなくてよかった) | 影響しない |
| `▲` 検査不能 | **実行できなかった**項目(検査したかったのにできなかった)。★**「納品物の形が原因」とは限らない**(誰が直せるかは規則ごとに違う——所在は右欄・`STATE_RESPONSIBILITY`〔`check_deliverable.py` 上部の表〕を参照) | 門番規則(uradori: U-0 / bunken: B-0 / html: H-0 / ronbun: R-0)が拾って違反を立てるので、結果として 1 になる。★2026-08-20 に**4種別すべてが on** になったので「門番が繋がっていない種別」は無い。★ただし `check_*()` の**外**で原典を失って ▲ になる経路は門番を通らず、`report()` が数えて **3** に出る。★★**2026-08-20(ユーザーの裁定): 責任が「チェッカー」の ▲(`crashed`= 検査処理そのものが例外で落ちた)は門番が拾わない。**納品物の欠陥ではないからである(`DESIGN.md` 柱2 の表)。**違反にしないだけで ▲ は残る**ので、`report()` が数えて**終了コードは 3(合格ではない)**になる。★★**2026-08-20(裁定・第2弾): 責任が「呼び出し」「人間」(規則未実装・原典喪失)の ▲ も同じに扱う** —— ✕ を立てるのは**責任=納品物 の ▲ だけ**である(`DESIGN.md` 柱2 の表の3行に統一した)。★**原典喪失の枝はそれまで「門番より後で立つ」という順序に守られていただけ**で、順序が変われば ✕ になる状態だった。いまは順序に依存しない(常設テスト E-18) |

この2つを1つの箱に入れていたことが F-046 の根本原因だった。両方を「未検査」と呼んでいる限り、
どちらを終了コードに繋いでも事故になる——前者を繋ぐと **html-visualizer は H-6 が構造上つねに未検査なので成果物が全件不合格**になり、
繋がなければ「検査の大半が実行されていないのに納品してよい合図が出る」状態が残る。

## 原典欄の読み方(★この欄は【生成物】。手で書き換えない)

**原典欄に行番号は書かない。**代わりに原典の**逐語**(`` ` `` で囲った文字列)が入っている。
その逐語を原典ファイルで検索すれば、規定そのものの位置に着く。

★**なぜ行番号をやめたか(実測)**: 行番号を書き写して持つと、原典が1行伸び縮みするだけで表が黙って腐る。
2026-08-17 の bunken 本体の改訂1回で8件が一斉にずれ、常設テスト D-6(行数を超えていないか)は素通りした。
検出する仕掛けを足しても**本体を1行足すたびに赤くなる**ので、やがて無視される
(`30-round-flow.md` §4-B「**通らないゲートは、偽陽性を出す検査と同じく『無いのと同じ』になる**」)。
**生成物にし、生成される中身から行番号を追い出せば、本体が伸び縮みしても規則表は動かない。**
逐語は原典に**ちょうど1回**あることを、実行時と常設テスト F-1 が別々に確かめている。

生成し直す(★**1コマンドで2つとも作り直す**。原典欄と控え以外の欄には触れない):

```bash
python "$HOME/.claude/skills/tools/checker/sync_rules_md.py"          # 生成して書き換える
python "$HOME/.claude/skills/tools/checker/sync_rules_md.py" --check  # 書き換えず差分だけ見る
python "$HOME/.claude/skills/tools/checker/sync_rules_md.py" --self-test  # 測定器自身の試験
```

★**生成の対象は2つある**(2026-08-18 に2つ目を追加):

| # | 何 | 中身 |
|---|---|---|
| 1 | この規則表の**原典欄** | 原典ファイルへのリンクと**逐語**。**行番号を1つも書かない** |
| 2 | `check_deliverable.py` の**控え** | `ORIGIN_FALLBACK` の値と `NOT_MECHANIZED` の第3要素。★こちらは `file:line` そのもの |

★**なぜ控えも生成物にしたか(実測)**: 2026-08-18 の段4で4スキルの原典に規定を5件足したところ、
**常設テストが5件赤くなった**。落ちたのは全部「控えだけが古い」型で、判定に関わる項目は0件だった。
さらに段4の**前**の原典で同じことをすると**23件**が同じ型で落ちた ——
つまり**本体を1行足すたびに人が控えを手で直す**形になっていた。
**照合する項目(F-9・F-11・E-4)だけでは「赤くなるが直せない」。照合と再生成は対で置く。**
★**控えを消して赤を消すのではない** —— 原典に到達できない環境でも検査が動くことを常設テスト **F-6** が
保証しており、控えが無いとそこで道具が死ぬ。**消さずに、作り直せるようにする**のが正解である。

★**生成の対象は、逐語を持つ項目だけ**である(どれが対象かは `check_deliverable.py` の `ORIGIN_QUOTES` が正)。
**逐語をまだ持たない項目の原典欄は、従来どおり手書きの `file:line` であり、生成もされず、
常設テスト F-4 の対象からも外れている** —— つまり**黙って腐りうる**。

★**「黙って」がどれくらい黙っているか(2026-08-18 の実測)**: `run-html-visualizer/SKILL.md` に**1行足す**と、
手書きだった H-1〜H-6 は**6本とも規定を指さなくなり、うち2本は空行を指した**。
それでも常設テストは **721項目中721合格のまま緑**だった —— 効いている検査 D-6 は
「行番号がファイルの**行数を超えて**いないか」しか見ないので、**ファイルが伸びる向きのずれは素通りする**。
**「テストが緑だから腐っていない」は成り立たない。**現物: `runs\checker\evidence\origin-after-growth-html6.txt`。

★**53規則はすべて逐語を持った**(2026-08-18)。★**同日、機械化を見送った項目8件も逐語を持った**
(残っていた4件= 単位「トン◎ / t×」・会社名・東京23区の区名・町村の県名。いずれも原典は `kosei-yogo.md`)。
**規則として実装していないことと、原典の指し先が腐ってよいことは別である** —— 用語集が1行伸びれば
見送り項目の原典欄も同じように腐るので、逐語にした。

★**常設テスト F-9 の歯止めは【架け替えた】**(2026-08-18。外していない):
**旧「逐語を持たない見送り項目は4件」→ 新「機械化見送り項目そのものが8件」。**
逐語化で旧の期待値は 4→0 になり役目を終えるが、**歯止めの目的は「見送り項目が黙って増えないこと」**
であって「逐語が無いこと」ではないので、目的のほうを残して数える対象を差し替えた。
見送りを増やすときは、この数を書き換える判断を通すことになる。
腐りを止めたい項目には `ORIGIN_QUOTES` に逐語を1句足す(足せば自動で生成と F-4 の対象に入る)。

★**原典欄の外に残っていた手書きも、同日すべて逐語にした**(申-2〜申-4)——
判定の理由に付く原典9個・水準表の原典欄4個・**この表の散文**7個。
とくに散文は生成の対象外なので、**行番号を持たない形**(逐語+ファイルへのリンク)に書き換えてある。
常設テスト **F-11** が「散文の逐語が原典にちょうど1回あるか」と
「**規則表のどこにも file:line が無いか**」の両方を毎回見る。
