# ref-nohin-checker — 納品物チェッカーの使い方

納品物チェッカー(`check_deliverable.py`)は、run-uradori の出典台帳・run-bunken-daicho の文献台帳・run-ronbun-shippitsu の原稿・run-html-visualizer の HTML が、それぞれのスキルの決まりに合うかを機械で照合する道具。規則の一覧は同じフォルダの `deliverable-rules.md`。このファイルはその使い方の説明書で、呼び出し元のスキルが納品の前に読む。ネットに出られない環境・チェッカーが無い環境でだけ要ることは `references/kankyo.md` に分けてある。

## 1. チェッカーの在り処

- 先に、このスキルのフォルダの `tools/checker/check_deliverable.py` を探す(配る束から入れた形。claude.ai などに上げた .skill と、`npx skills add` で入れたスキル。束を作る時に入り、手元のこのフォルダには無い)。この形で走らせる時は、2 の命令の頭に `CHECKER_SKILLS_ROOT="<このスキルのフォルダの1つ上>"` を付ける(チェッカーは自分の2つ上を規則の出どころのスキル置き場と見なすので、付けないと「原典に到達できない」が毎回1件出る。合否は同じ)。
- 無ければ、スキル置き場の `tools/checker/check_deliverable.py`(`$HOME/.claude/skills/tools/checker/check_deliverable.py`。作者の PC の形)。この順にするのは、前の版の束をコピーで入れた PC に、ここへ古いチェッカーが残っていることがあるため。
- どちらにも無いときだけ、`references/kankyo.md` の目視の代替に切り替える。「チェッカーが無いから省略した」で終わらせない(省略すると、何が確かめられていないかが読み手に1つも伝わらない)。

## 2. 走らせ方

| 呼び出し元 | 走らせる段階 | コマンド(`<チェッカー>` は 1 で見つけたパス。`uv run --with pymupdf==1.27.2.3` は、PDF を読む部品をこの版で用意して走らせる形で、使う人の PC の Python は変えない。`uv` の無い環境(claude.ai など)では `python` に替える(`python` の名前で Python 3 が動かない環境(Mac・Linux など)では `python3`)) |
|---|---|---|
| run-uradori | A・C | `uv run --with pymupdf==1.27.2.3 <チェッカー> <台帳.md> --type uradori --links <作業用フォルダ>/links.json --fetch-links --fulltext <作業用フォルダ>/fulltext.json --fetch-fulltext` |
| run-bunken-daicho | A・B・C | `uv run --with pymupdf==1.27.2.3 <チェッカー> <台帳.md> --type bunken --links <作業用フォルダ>/links.json --fetch-links --biblio <作業用フォルダ>/biblio.json --fetch-biblio --shoshi <台帳名>.shoshi.json --fulltext <作業用フォルダ>/fulltext.json --fetch-fulltext` |
| run-ronbun-shippitsu | (段階なし) | `uv run --with pymupdf==1.27.2.3 <チェッカー> <原稿.md> --type ronbun` |
| run-html-visualizer | (段階なし) | `uv run --with pymupdf==1.27.2.3 <チェッカー> <出力.html> --type html --expect-count N --count-pattern RE`(アーティファクトとして出したものは `--artifact` も付ける) |

- run-ronbun-shippitsu・run-html-visualizer は段階A/B/Cを走らせないので、4 の申告の囲みは要らない。3 の印の読み方と止まり方は同じ。
- run-html-visualizer の `--expect-count N --count-pattern RE` は、付けないと全量保持が未検査のまま残り、終了コードが 3 になる。N は入力から数えた件数、RE は HTML の中でその単位を数える正規表現(選び方は run-html-visualizer の本文)。

- 段階A= リンクが現に届くか/段階B= 書誌が DOI(論文ごとの固定の識別番号)の登録機関の記録と合うか(run-bunken-daicho だけ)/段階C= 引いた逐語が原典に在るか。
- `--shoshi` は書誌の項目ファイル(run-bunken-daicho の台帳の JSON と同じフォルダ。チェッカーに渡す Markdown は作業用フォルダにあるので、別の置き場になる。`scripts/shoshi.py` が書く)。渡すと段階Bが年・題名・頁・出版社も照らし、書誌欄が項目ファイルの値を持っているかも見る。読めないファイルを渡すと終了コード 2。
- `--fetch-…` が、原典を取りに行く指定である。外して走らせると、その段階は原典を1本も見ないまま「取得結果が渡されていない」で未検査になる。
- 作業用フォルダは納品物の外に置く(段階Cの取得結果には原典の本文が入り、納品物と一緒に渡すと原典の全文を配ることになるため)。
- 申告の囲み(4)を貼ったあとの通し直しは、同じ置き場を渡したまま `--fetch-…` だけを外す(取り直さず、1回目に取った結果で同じ申告を出させる。取り直すと、ページの変化で申告と台帳がずれるため)。台帳の逐語やリンクを足し替えたときだけは、`--fetch-…` を付けて取り直す。
- ★**PyMuPDF が無い環境(claude.ai など)では、上の機械照合を走らせる前に `pip install pymupdf` で入れる**(段階Cが本文PDFを読む道具。無いと PDF の本文を1本も読めない)。pip で入れるのは、claude.ai の作業場のように使う人の PC でない所だけ。Claude Code では上の表のとおり `uv run --with` が PyMuPDF をこの版で用意するので、使う人の PC の Python に pip で入れる道は使わず、uv が無ければユーザーに uv を入れてもらう(段階Cが本文PDFを読む道具。無いと PDF の本文を1本も読めない)。

## 3. 結果の読み方と止まり方

| 印 | 意味 | 終了コード | 納品 |
|---|---|---|---|
| ✕ | 違反 | 1 | しない。直してから通し直す |
| ▲ | 検査不能(測れなかった) | 3(✕が無いとき) | しない |
| ― | 未検査 | 出力に「検査は終わっていない」と出た「―」は 3(✕が無いとき)。ほかの「―」は効かない | 出力に「検査は終わっていない」と出た「―」が残れば しない。ほかの「―」(規定によりこの納品物に当てない項目)では止めない |
| △ | 要目視 | 効かない | 指摘の当否を自分で判断する |
| (印なし) | 引数の誤り・取得結果のファイルが読めない(検査は1本も走っていない) | 2 | しない。出力のエラー文を読み、コマンドか置き場を直して通し直す |

- ▲と、出力に「検査は終わっていない」と出た―が残ったら、何が検査されなかったのかを出力で読み、書式を直してから通し直す。終了コード 3 は「検査できなかった項目が残っている」で、「違反が無かった」ではない。
- 段階Cの「測れなかった」は、書式を直しても消えない(本文を取れなかった、または本文と言えないページ=案内ページや判定不能のページにしか当てられなかった、という意味である)。そのときも納品しない。代わりに、チャットの返答の本文に、段階Cの囲みの「測れなかった」の一覧(行・引用・理由・当てたページの URL と種別)を1件も落とさずに並べ、ユーザーの判断を待つ。依頼者は台帳を基本的に読まず、台帳の中に書いただけでは届かないためである(ユーザー裁定 2026-09-24)。run-bunken-daicho だけは例外があり、当たるかはその `scripts/daicho.py … reigai` が決める(その SKILL.md の工程4 の8)。
- 段階A・段階Bの未検査(測れなかったもの)が残ったときも、同じ形で止まる。チャットの返答の本文に、その段階の囲みの未検査の一覧(段階・行・リンクまたは DOI・理由)を1件も落とさずに並べ、ユーザーの判断を待つ(ユーザー裁定 2026-09-28)。
- ネットに出られない環境では、印の出方が変わる(名前(ドメイン)が引けないと、段階Aが全リンクを ✕ に数える)。そのときの扱いは `references/kankyo.md` の 1。
- run-uradori の台帳では、出力の「台帳本体= 表n つ・m 行を検査」の m が台帳の実際の行数と一致していることを確かめる(役が決まらない表は検査に入らず、出力の注記にだけ出るため)。

## 4. 申告の囲み(段階ごとに1つ。納品物とチャットの両方に)

機械照合の出力の末尾に、段階ごとに「stage-a v1」「stage-b v1」「stage-c v1」という印の付いた囲みが出る。呼び出し元が走らせた段階の囲みを、すべて貼る。

### 4-1. どの段階にも共通

- その囲みを、行を落とさず・順番も変えずに、台帳本体の表より後ろへそのまま貼る。あわせて納品のチャット本文にも写す(呼び出し元のスキルが写し方を決めている時はそちらに従う。run-bunken-daicho は段ごとの数の行と測れなかった物の一覧を写す)。画面に出たことは、申告したことにならない(依頼者はチャットしか見ないことがあり、何が確かめられていないかを知らないまま台帳を使ってしまう)。
- 未検査・測れなかったものが0件のときも「★未検査 0件」「★測れなかった 0件」の行ごと貼る(貼らないと、読み手には「確かめた結果として0件だった」のか「申告し忘れた」のかが区別できない)。
- 表より前に置かない(申告文の中の行番号が動き、貼り直しても一致しなくなる)。
- ★**囲みを空にしない。**空にすると、次に誰かがチェッカーを掛けても「走らせていない」と「申告し忘れた」が区別できない。チェッカーが無い環境で貼る3行は `references/kankyo.md` の 2。
- 同梱したかはチェッカーが毎回確かめる。チャットに貼ったかは確かめられない(自分の出力がチャットへ写されたかは走行から観測できない)。そこだけが人手の掟である。

### 4-2. 段階A

段階Aの申告ブロックを、納品物に必ず同梱する(省略不可)。

### 4-3. 段階B(run-bunken-daicho だけ)

段階Bの申告ブロックを、納品物に必ず同梱する(省略不可)。

- ★**この囲みは段階Aのものとは別に置く**——段階Aと段階Bは別々に走りうるので、片方だけ走らせた走行の申告を、もう一方の申告に見せかけないためである。
- この関門が見るのは、DOI を持つ行の書誌だけ(項目ファイルが無ければ7項目のうち3項目= 著者名・誌名・巻(号))であり、run-bunken-daicho の工程5(書誌の突き合わせ)を1文字も減らさない。

### 4-4. 段階C

段階Cの申告ブロックを、納品物に必ず同梱する(省略不可)。

- この囲みも、段階A・段階Bのものとは別に置く(段階Aと段階Cは別々に走りうるため)。
- ★**逐語の引用が1本も無い台帳でも貼る**——「照合するものが無かった」と「申告し忘れた」は、読み手には区別できない。
- この段の合格は「0件」ではない。「取れたものについて0件」と、取れなかった件数がセットである。
